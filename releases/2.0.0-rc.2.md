# PlexonKeys 2.0.0-rc.2 — Phase 3 Reliability Candidate

PlexonKeys 2.0.0-rc.2 hardens the Phase 2 candidate after production showed that an upgraded configuration could still run with shutdown-only persistence.

## Reliability correction

- Existing configurations with legacy `storage.checkpoint-seconds: 0` now inherit a production-safe 60-second effective checkpoint interval.
- Periodic checkpointing can still be disabled intentionally through `storage.checkpoints.enabled: false`.
- Reload always cancels the previous checkpoint task before scheduling the replacement; there is one shared scheduler, never one task per player, key, block, or event.
- Checkpoints reuse the existing single bounded database worker, queue capacity 1, revision-aware save coalescing, and bounded immutable delta snapshots.
- Failed writes remain dirty and retryable; controlled plugin disable still drains a final save.

## Crash-durable consume and claim boundaries

- Public/API `consume(..., transactionId)` no longer relies on a process-local replay map.
- Consume transaction IDs are persisted with their player, tier, amount, and creation time.
- A successful balance debit and its replay record share one memory revision and are selected into the same SQLite transaction before `SUCCESS` is returned.
- Exact duplicate transaction IDs cannot debit twice after restart.
- Conflicting reuse of a transaction ID fails closed.
- Replay retention is bounded to 4,096 persisted records and seven days; an unsaved overflow is capped so a failed database cannot create an unbounded replay cache.
- Physical `/keys` claims durably commit their virtual debit before inventory delivery. If delivery fails, the virtual debit is restored and the compensation is persisted.

## Database migration

Database schema moves from **1 to 2** only to add the bounded `consume_replay` idempotency table and its timestamp index.

Before the first schema-1 migration, PlexonKeys creates:

`plexonkeys.db.pre-v2.bak`

The backup is created once and is not overwritten. Existing `players` and `placed_blocks` tables are retained in place; balances, player names, and placed-block provenance are not destructively rewritten. Migration is idempotent and newer unknown schemas remain rejected.

SQLite remains configured for one transactional writer with `journal_mode=DELETE`, `synchronous=FULL`, and a busy timeout. RC2 does not introduce WAL, a second executor, or synchronous persistence in `BlockBreakEvent`.

## Provenance safety

- Existing local/Core ownership behavior is unchanged.
- Player-placed/derived artificial coordinates remain persisted in `placed_blocks`.
- Normal crash exposure for newly dirty provenance is now bounded by the effective checkpoint interval, with the existing pressure-triggered early checkpoint retained for large mutation bursts.
- UNKNOWN provenance remains fail-closed by default.
- No destructive rescan or rewrite of large existing provenance datasets is introduced.

## Diagnostics

`/keysadmin diagnostics` now exposes:

- persistence mode and SQLite schema;
- checkpoint enabled state and effective interval;
- dirty account/block/replay counts;
- current/requested/acknowledged revisions;
- in-flight/requested persistence state;
- worker queue depth, high-water mark, and capacity;
- last successful and failed save timestamps;
- save timings/failures;
- tracked blocks/player count;
- replay record count, retention limit, and retention period.

## Performance boundary

The Phase 3 fix does **not** perform Pipeline 1's global event-routing redesign. Mining/logging/fishing/mob acquisition remains memory-only on the event path and persists through asynchronous checkpoints. Critical durability barriers exist only at low-frequency irreversible consume/physical-claim boundaries and still execute SQLite work on the existing database worker.

## Upgrade / runtime certification

1. Stop PlexonCraft cleanly.
2. Back up the active PlexonKeys JAR and complete `plugins/PlexonKeys/` directory.
3. Replace only the JAR with `PlexonKeys-2.0.0-rc.2.jar`; keep the existing configuration and `plexonkeys.db`.
4. Start on Paper 26.2 build 121 / Java 25 / PlexonCore 2.0.4.
5. Verify the schema-1 pre-migration backup exists if the previous database was schema 1.
6. Run `/keysadmin diagnostics` and verify checkpoints are enabled at 60 seconds unless explicitly disabled.
7. Verify balances and the large placed-block provenance dataset survived migration.
8. Exercise periodic checkpoint + restart, forced-crash recovery, physical claim, exact transaction retry, conflicting transaction ID, PlexonCrates consume integration, and UNKNOWN provenance behavior.
9. Confirm no SQLite/file I/O was added to BlockBreakEvent and compare MSPT/TPS against the prior candidate.

**RUNTIME CERTIFICATION REQUIRED.** This is a prerelease candidate only. Do not merge to `main` or promote `v2.0.0` stable from CI evidence alone.

## Rollback

`v2.0.0-rc.1` remains immutable. The stable rollback baseline remains `v1.4.1` (`c06a9e4107fc259f45d32d1f0767e5e2b5d1d872`). If runtime certification fails after schema migration, stop the server and restore the backed-up JAR together with the corresponding pre-upgrade data directory; do not combine an older binary with a partially migrated live database.
