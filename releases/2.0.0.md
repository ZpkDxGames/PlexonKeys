# PlexonKeys 2.0.0

Stable GitHub repository closure of the accepted PlexonKeys 2.0 premium key/provenance line and Phase 3 reliability candidate, plus one configuration-runtime rollback fix discovered during the final source audit.

## Product boundary

PlexonKeys 2.0 keeps the established first-party key authority model:

- stable key IDs: `basic`, `rare`, `epic`, `legendary`;
- memory-authoritative virtual balances;
- exact physical `ItemStack` identity and safe claim delivery;
- PlexonCore/local block provenance ownership with UNKNOWN fail-closed by default;
- natural/spawner/unknown mob provenance policy;
- Bukkit service API, events and PlaceholderAPI integration;
- bounded asynchronous persistence outside high-frequency activity event paths.

## Reliability retained from RC2

- legacy shutdown-only checkpoint configurations inherit a production-safe 60-second effective checkpoint unless checkpoints are explicitly disabled;
- public/API consume transaction IDs are persisted with player, key tier, amount and timestamp;
- successful consume debit + replay record share one memory revision and one SQLite transaction;
- exact duplicate consume transaction IDs cannot debit twice after restart;
- conflicting transaction-ID reuse fails closed;
- consume replay retention is bounded to 4,096 records and seven days;
- physical claims durably commit the virtual debit before inventory delivery and persist compensation if delivery fails;
- one bounded persistence worker remains authoritative, with coalesced revision-aware saves and retryable failed writes;
- schema-1 databases migrate transactionally to database schema 2 with the one-time `plexonkeys.db.pre-v2.bak` safety copy.

## Final stability fix

Configuration parsing was already candidate-based, but subsystem application was not previously transactional. A validated configuration could become active and partially rebuild menus, rewards, economy, checkpoint scheduling or Core block ownership before a later runtime-application step failed.

Stable 2.0 closes that boundary:

- the last runtime-accepted `Settings` and config bytes remain available until subsystem application succeeds;
- successful application explicitly accepts the candidate;
- failed application restores the last-good runtime settings and rebuilds the previous subsystem state;
- internal in-game configuration edits restore the exact previous `config.yml` bytes on failure;
- externally edited files are intentionally left on disk for correction while the previous runtime remains active;
- configuration revision remains monotonic through rollback so stale GUI sessions/caches cannot become authoritative again;
- checkpoint scheduling is rebuilt without leaking duplicate tasks.

## Stable publication verification

Stable publication runs only when `release/stable` points to exact current `main`. The workflow:

1. proves accepted RC2 ancestry;
2. provisions checksum-pinned PlexonCore 2.0.4;
3. rebuilds exact source with `mvn clean verify`;
4. requires a non-empty, zero-failure/error/skip JUnit suite;
5. verifies installable JAR contents, SQLite packaging, Java major 69 and provided-integration isolation;
6. publishes `PlexonKeys-2.0.0.jar`, `SHA256SUMS.txt`, `TEST_SUMMARY.txt` and `PROVENANCE.txt`;
7. downloads those public release assets;
8. verifies the published checksum, exact source SHA, accepted RC2 lineage and reliability provenance before the Release workflow can pass.

Historical `v2.0.0-rc.1` and `v2.0.0-rc.2` remain immutable evidence. The stable rollback baseline remains `v1.4.1` at `c06a9e4107fc259f45d32d1f0767e5e2b5d1d872`. The immediate historical RC2 artifact is `v2.0.0-rc.2` from accepted source `f5f8656a4cc879e449a8b822386892a659d8e228`, JAR SHA-256 `0cc87449754b7e5dec34e57091f856f2bfa98a3c256eb41617b510911cbe0ee4`.

Live PlexonCraft migration, acquisition, cross-plugin, crash-recovery, MSPT and soak validation remains a deployment follow-up. Stable release provenance may therefore record `runtime_certification=NOT_EXECUTED`; live evidence is never inferred from CI.
