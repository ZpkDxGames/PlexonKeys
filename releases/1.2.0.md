PlexonKeys 1.2.0 migrates the existing production key system into the PlexonCore ecosystem without replacing its gameplay, database, configuration, or captured physical key format.

### PlexonCore migration

- Optional PlexonCore 1.0.0 integration with safe `CORE` and `STANDALONE` modes.
- Core module ID `keys`, health states, lifecycle registration/unregistration, and `PLEXON_KEYS` integration capabilities.
- `/keysadmin diagnostics` for Core/API/storage/event visibility.
- Core remains a `provided` compile dependency and is not bundled into the plugin JAR.

### Public API and native PlexonQuests events

- New Bukkit `PlexonKeysAPI` service for balances, capped grants, removals, tier state, and defensive key-template access.
- New `KeySource` acquisition metadata.
- New `PlexonKeyEarnedEvent` fired only after a real virtual balance increase.
- New `PlexonKeyClaimedEvent` fired only after virtual debit and physical inventory delivery both commit.
- Claim-all emits one event per delivered tier, sharing a parent transaction ID while keeping unique per-tier event IDs.
- Activity sources are stable machine IDs such as `activity:mining`; normal claims use `player-claim`.
- Failed claims restore balances silently, so rollback cannot create false quest progress.

These event classes satisfy the public reflection contract used by PlexonQuests 3.1.0 for `PLEXON_KEY_EARN` and `PLEXON_KEY_CLAIM` objectives.

### Compatibility and safety

- Existing `plugins/PlexonKeys/plexonkeys.db` remains authoritative.
- Existing configuration paths and values remain compatible.
- Existing Basic/Rare/Epic/Legendary balance behavior, chances, cooldowns, reward bonuses, GUIs, and tracked-block protection are preserved.
- Captured external-plugin key ItemStacks remain full Paper binary item snapshots.
- Listener exceptions after a committed award/claim are isolated so they cannot duplicate physical keys or undo committed state.

### Build verification

The release workflow uses Java 25, downloads the official PlexonCore 1.0.0 release JAR, verifies its pinned SHA-256, installs it only as a Maven compile dependency, runs the complete Maven test suite, verifies the packaged API/event classes and SQLite driver, confirms Core runtime classes are absent, and creates `SHA256SUMS.txt`.

Before production deployment, follow `docs/MIGRATION_1.2.0.md` and complete the Core + Quests staging checks.
